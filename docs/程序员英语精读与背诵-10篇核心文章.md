# 程序员英语精读与背诵：10 篇核心文章

> 编写日期：2026-10-12  
> 用途：朗读、背诵、复述，以及软件开发英文文档阅读训练。  
> 内容性质：围绕经典的软件开发主题原创编写的学习短文，不是摘录的名家名篇，也不是官方文档原文。每篇附有相关的一手技术资料，供进一步阅读。

这套材料把 README、入门教程、API 说明、故障排查和开发指南中反复出现的表达，组织成有上下文的短文。主线是一名开发者从运行项目，到实现功能、处理故障、测试发布，再到改进系统的过程。

每篇英文正文约 200 词，分成 4 个自然段。建议先把每段读懂、读顺，再连接成整篇。文中会有意重复 `require`、`provide`、`return`、`allow`、`handle` 等高频动词，并在不同场景中使用它们。

背熟少量文章有助于积累表达，但不能保证仅靠背诵就大幅提高听说读写。这里把背诵和实际文档阅读、听音模仿、口头复述结合起来：最终目标是看懂新的文档，而不只是记住这十篇。

## 如何用这套材料

每次练习可以控制在 20～30 分钟，根据自己的基础调整。

1. **读懂**：先读英文，标出不理解的句子；再对照译文，确定主语、动作、条件和结果。
2. **读顺**：每次读一个自然段。遇到条件从句、转折词、并列项时稍作停顿，不要按每个单词机械停顿。
3. **听与模仿**：搭配清晰的英语音频，先听后读，再跟读。若用语音合成，缩写和专业词的读法需要额外核对。
4. **回忆**：遮住英文，根据中文或段落关键词复述。先保证意思正确，再练习恢复原句。
5. **迁移**：完成每篇末尾的任务，使用文章句型描述自己的项目。
6. **接触原文**：打开延伸阅读，只选一个小节，找出与短文相似的表达。

可采用“当天学习，次日、第 4 天、第 8 天复习”的节奏。这是便于执行的安排，不是唯一或保证有效的记忆公式。能正确复述段落意思后，再逐渐追求完整背诵。

### 阅读技术文档时，特别留意这些词

| 表达 | 阅读时要识别的含义 |
|---|---|
| must / required | 必须满足的要求 |
| should / recommended | 建议或预期；强度通常低于 must |
| may / can | 可能性、许可或能力，要结合上下文 |
| by default | 没有另外配置时的行为 |
| unless | 除非；引入例外条件 |
| otherwise | 否则；说明另一种情况 |
| provided that | 只要；前提是 |
| is used to / is designed to | 用途 / 设计目的 |
| returns / raises / throws | 返回结果 / 引发异常 |
| deprecated / removed | 已不推荐使用 / 已移除，两者不同 |

## 01. Getting a Project Running

**主题：环境与依赖。背诵线索：阅读说明 → 安装依赖 → 启动检查 → 记录步骤。**

### 英文正文

Before you change a project, make sure you can run it. Start with the README and look for the required runtime, installation steps, and startup command. A project may depend on a specific version of a language or tool. Using a different version can lead to unexpected behavior.

Next, install the dependencies in the way the project recommends. A dependency is a package that the application needs in order to work. Some projects also require a separate environment. In Python, for example, a virtual environment allows different projects to use different versions of the same package.

Once installation is complete, start the application and check its output. A message saying that the server is ready is a useful sign, but you should also open the page or call an endpoint. This confirms that the application can respond to a real request. If startup fails, read the first relevant error before changing anything.

Finally, write down the steps that worked. Include any required settings and explain how to stop the application. Another developer should be able to follow the same instructions without guessing. A clear setup guide saves time because it turns personal experience into a process that the whole team can repeat.

### 中文对照

1. 修改项目之前，先确保自己能够把它运行起来。从 README 开始阅读，找到所需的运行时、安装步骤和启动命令。项目可能依赖某个特定版本的语言或工具。使用不同版本可能导致意外行为。
2. 接下来，按照项目推荐的方式安装依赖。依赖是应用正常工作所需的软件包。有些项目还要求使用独立环境。例如，在 Python 中，虚拟环境允许不同项目使用同一个软件包的不同版本。
3. 安装完成后，启动应用并检查输出。“服务器已就绪”这样的消息是一个有用的信号，但你还应该打开页面或调用一个接口端点。这样才能确认应用确实能够响应实际请求。如果启动失败，先阅读第一条与问题相关的错误，再进行修改。
4. 最后，记录成功运行的步骤。写明必要的设置，并解释如何停止应用。另一位开发者应该能够按照相同的说明操作，而不必猜测。清晰的环境搭建指南可以节省时间，因为它把个人经验转化成整个团队都能重复执行的流程。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| runtime | 运行时、运行环境 | runtime version：运行时版本 |
| require / required | 要求 / 必需的 | requirement：要求、必要条件 |
| dependency | 依赖项 | depend on：依赖；dependent：依赖的 |
| specific | 特定的 | a specific version：特定版本 |
| installation | 安装 | install：安装；installer：安装程序 |
| virtual environment | 虚拟环境 | environment：环境 |
| endpoint | 接口端点 | call an endpoint：调用接口端点 |
| startup | 启动 | startup command / startup failure |

### 文档句型拆解

- **A project may depend on a specific version of a language or tool.** `may` 表示可能；`depend on` 后接依赖的对象。可迁移为：`This feature depends on an external library.`
- **Once installation is complete, start the application.** `Once + 从句` 表示“一旦……完成”。前半句是条件或时间，后半句是操作。可迁移为：`Once the build is complete, run the tests.`
- **Another developer should be able to follow the same instructions.** `should be able to` 表示预期应当具备的能力。可迁移为：`The client should be able to reconnect automatically.`

### 复述与迁移

- 不看原文，用英语说明：为什么看到“server is ready”后，还需要打开页面？
- 用 `requires`、`depends on`、`once` 各写一句话，描述你自己的项目如何启动。

**延伸阅读：** [Python 官方教程：Virtual Environments and Packages](https://docs.python.org/3/tutorial/venv.html)。练习寻找 `require`、`version`、`environment`，阅读虚拟环境解决依赖冲突的说明。

## 02. Configuring an Application

**主题：配置与默认值。背诵线索：代码与配置 → 默认与覆盖 → 校验 → 配置说明。**

### 英文正文

The same application may run on a developer's laptop, a test server, and a production server. Its basic behavior can remain the same, while its database address, port, and other settings change. Keeping these values separate from the application code makes it easier to use the software in different environments.

A setting may have a default value. The application uses that value unless you provide another one. For example, a service might listen on port eight thousand by default. An environment variable can override this setting, provided that the application is designed to read it. The documentation should explain which source takes priority.

Configuration also needs validation. If a required value is missing, the application should report the problem clearly. If a value has the wrong format, the error should identify the setting and describe the expected format. A useful error helps the developer correct the input without searching through unrelated code.

Treat configuration instructions as part of the product. For every option, explain its purpose, default value, and allowed values. State whether a restart is required after a change. Use safe examples instead of real passwords or access tokens. Good configuration documentation answers a practical question: what must I provide before this application can work in my environment?

### 中文对照

1. 同一个应用可能运行在开发者的笔记本电脑、测试服务器和生产服务器上。它的基本行为可以保持不变，而数据库地址、端口和其他设置会发生变化。把这些值与应用代码分开，可以更方便地在不同环境中使用软件。
2. 某项设置可能有默认值。除非你提供其他值，否则应用就使用该默认值。例如，某个服务可能默认监听 8000 端口。环境变量可以覆盖这项设置，前提是应用本身被设计为会读取该变量。文档应该解释哪个配置来源具有更高优先级。
3. 配置同样需要校验。如果缺少必填值，应用应该清楚地报告问题。如果值的格式不正确，错误信息应该指出是哪项设置，并说明预期格式。有用的错误信息可以帮助开发者修正输入，而不必到无关的代码里四处查找。
4. 要把配置说明视为产品的一部分。对每个选项，都应解释其用途、默认值和允许的取值。说明修改之后是否需要重启。使用安全的示例值，而不是真实的密码或访问令牌。好的配置文档会回答一个实际问题：要让应用在我的环境中工作，我必须提供什么？

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| configuration | 配置 | configure：配置；configurable：可配置的 |
| production | 生产环境；正式运行阶段 | production server：生产服务器 |
| default value | 默认值 | by default：默认情况下 |
| override | 覆盖原有设置 | 本文是配置覆盖，不是方法重写 |
| environment variable | 环境变量 | variable：变量 |
| take priority | 优先；具有更高优先级 | priority：优先级 |
| validation | 校验 | validate：校验；valid：有效的 |
| access token | 访问令牌 | token 在不同领域含义不同 |

### 文档句型拆解

- **The application uses that value unless you provide another one.** `unless` 表示“除非”，可理解为 `if you do not provide another one`。不要把例外条件读成必做步骤。
- **An environment variable can override this setting, provided that the application is designed to read it.** `provided that` 引出成立前提；`is designed to` 说明设计用途。不是所有应用都会自动读取任意环境变量。
- **State whether a restart is required after a change.** `whether` 引导“是否……”；`is required` 是被动表达。可迁移为：`Check whether authentication is required.`

### 复述与迁移

- 用英语解释 `default value` 和 `override` 的区别。
- 为自己的项目写一项配置说明，包含用途、默认值，以及是否需要重启。

**延伸阅读：** [The Twelve-Factor App：Config](https://12factor.net/config)。关注代码与部署配置分离的思想。本篇的 8000 端口只是示例，不是通用默认端口。

## 03. Understanding an API Request

**主题：请求与响应。背诵线索：请求组成 → 校验处理 → 响应内容 → 调用说明。**

### 英文正文

When a client needs information from a service, it sends a request to an endpoint. The request identifies an action and the resource involved. In an HTTP API, the method and URL help describe that action. Headers carry additional information, and some requests include a body containing the data to be processed.

Consider a task management application. To create a task, the client sends a title and an optional description. The server checks whether the title is present and whether the input is valid. It should also check whether the caller is allowed to create the task before making the requested change.

The server then returns a response. A successful response might include the new task's identifier and its current status. An unsuccessful response should help the client understand what went wrong. The HTTP status code provides a general signal, while the response body can provide details that are specific to the application.

Good API documentation describes both sides of this exchange. It lists required fields, explains optional values, and shows examples of successful and unsuccessful responses. It also states which errors the caller can handle. Before integrating an API, read these details carefully. A request that works in one example may fail when the input or the caller's permissions change.

### 中文对照

1. 当客户端需要从服务获取信息时，它会向某个端点发送请求。请求指明要执行的操作以及涉及的资源。在 HTTP API 中，请求方法和 URL 共同帮助描述该操作。请求头携带额外信息，有些请求还包含请求体，其中放着待处理的数据。
2. 以一个任务管理应用为例。创建任务时，客户端发送标题以及可选的描述。服务器检查标题是否存在，以及输入是否合法。在执行所请求的修改之前，它还应该检查调用者是否有权创建该任务。
3. 然后，服务器返回响应。成功的响应可能包含新任务的标识符及其当前状态。失败的响应应该帮助客户端理解出了什么问题。HTTP 状态码提供一个总体信号，而响应体可以提供与具体应用有关的详细信息。
4. 好的 API 文档会说明这次交互的双方。它列出必填字段，解释可选值，并展示成功与失败响应的示例。它还会说明调用方可以处理哪些错误。集成 API 之前，要仔细阅读这些细节。在某个示例中能够成功的请求，在输入或调用者权限改变时，可能会失败。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| client / server | 客户端 / 服务器 | client-side / server-side |
| request / response | 请求 / 响应 | send a request；return a response |
| resource | 资源 | 此处指接口操作涉及的对象 |
| header / body | 请求或响应的头部 / 主体 | body 在此不是“身体” |
| optional | 可选的 | 与 required 相对 |
| identifier | 标识符 | identify：识别、确定 |
| status code | 状态码 | HTTP 状态码与任务业务状态不同 |
| integrate | 集成、接入 | integration：集成 |

### 文档句型拆解

- **Some requests include a body containing the data to be processed.** `containing...` 修饰 `body`；`to be processed` 修饰 `data`，表示待处理的数据。先抓住主干：`requests include a body`。
- **It should also check whether the caller is allowed to create the task.** `check whether...` 表示检查是否；`be allowed to` 表示被允许做某事。
- **The response body can provide details that are specific to the application.** `that...` 修饰 `details`；`specific to` 表示某对象特有的。可迁移为：`This option is specific to the database driver.`

### 复述与迁移

- 用英语说明一次“创建任务”的请求和响应中可以分别包含什么。
- 为你熟悉的接口写三句话：需要哪些输入、成功时返回什么、失败时如何表示错误。

**延伸阅读：** [MDN：Overview of HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)。重点阅读消息中的请求与响应结构；本文的任务接口是原创教学场景。

## 04. Keeping Data Consistent

**主题：数据与事务。背诵线索：关联操作 → 事务边界 → 提交回滚 → 明确保证。**

### 英文正文

Many features require more than one change to stored data. When a user creates a project, an application may insert a project record and another record identifying its owner. If only the first operation succeeds, the database may contain a project that no one can manage. The two changes belong together.

A database transaction provides a way to group related operations. Instead of treating each operation as a separate result, the application defines a boundary around the work. When the transaction commits, its changes become permanent according to the database's durability guarantees. If it rolls back, the changes made within that transaction are discarded.

This does not mean that every action performed by the application is covered. Sending an email is not automatically undone when a database transaction rolls back. The application must consider such external effects separately. Otherwise, a user might receive a confirmation message for a project that was never successfully created.

When reading database documentation, pay attention to the scope of each guarantee. Look for explanations of transactions, constraints, and isolation levels. Ask what happens when an operation fails or when two users modify related data. Reliable software depends on understanding these boundaries. A feature is not complete merely because it works when every step succeeds.

### 中文对照

1. 许多功能需要对已存储的数据进行不止一次修改。用户创建项目时，应用可能插入一条项目记录，再插入另一条用于标识项目所有者的记录。如果只有第一步成功，数据库里就可能出现一个无人能够管理的项目。这两项修改应该作为一个整体处理。
2. 数据库事务提供了一种把相关操作组织在一起的方式。应用不再把每项操作当作独立的结果，而是在这些工作周围划定一个边界。事务提交后，其中的修改会依据数据库的持久性保证被持久保存。如果事务回滚，那么该事务内的修改就会被撤销。
3. 这并不意味着应用执行的所有动作都在事务的覆盖范围内。数据库事务回滚时，已经发送的邮件不会自动被撤回。应用必须单独考虑这些外部影响。否则，用户可能收到一封确认邮件，但邮件中的项目实际上从未成功创建。
4. 阅读数据库文档时，要留意每项保证的适用范围。寻找有关事务、约束和隔离级别的说明。思考操作失败时，或者两个用户修改相关数据时，会发生什么。可靠的软件依赖于对这些边界的理解。一个功能不能仅因为所有步骤都成功时能够运行，就被视为已经完成。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| record | 数据记录 | insert a record：插入记录 |
| transaction | 事务 | database transaction：数据库事务 |
| boundary | 边界、范围界限 | transaction boundary：事务边界 |
| commit / roll back | 提交 / 回滚 | rollback 是名词形式 |
| durability | 持久性 | durable：持久的 |
| discard | 丢弃、撤销而不保留 | discard changes：放弃修改 |
| constraint | 约束 | a unique constraint：唯一性约束 |
| isolation level | 隔离级别 | isolate：隔离；isolation：隔离 |

### 文档句型拆解

- **The database may contain a project that no one can manage.** `that...` 是修饰 `project` 的定语从句。可迁移为：`The response contains a field that the client does not recognize.`
- **Sending an email is not automatically undone when a database transaction rolls back.** `Sending an email` 整体作主语；`is undone` 是被动语态。抓住主干后再读 `when` 条件。
- **A feature is not complete merely because it works when every step succeeds.** `not...merely because...` 表示“不能仅仅因为……就……”。这是理解技术讨论中限制条件的常见结构。

### 复述与迁移

- 用英语解释：为什么“保存项目”和“发送邮件”不能简单地当作一个数据库事务来理解？
- 选一个需要多次写入的功能，说明哪些修改应该一起成功或一起失败。

**延伸阅读：** [PostgreSQL 官方教程：Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html)。关注事务的整体性和 `COMMIT`、`ROLLBACK`。事务的具体持久性与隔离保证还需结合数据库配置和相应文档阅读。

## 05. Finding the Cause of a Failure

**主题：错误与调试。背诵线索：复现 → 阅读错误 → 错误处理 → 回归验证。**

### 英文正文

When a program fails, changing code immediately is often less useful than gathering evidence. First, describe the expected behavior and the actual result. Then find a small, repeatable set of steps that produces the problem. A failure that can be reproduced is easier to investigate than one described only as something that sometimes goes wrong.

Read the error message carefully. An exception usually has a type and a message, and a stack trace can show the sequence of function calls that led to the failure. The location where an error appears is not always the place where the underlying mistake was made. Invalid data may have entered the system much earlier.

Handle errors at a level that can respond meaningfully. A user interface may show a helpful message, while a lower layer reports the cause to its caller. Catching every exception and ignoring it can hide broken behavior. Cleanup may still be necessary, so resources such as open files should be released even when an operation fails.

After identifying the cause, make a focused change and repeat the original steps. Add a regression test when appropriate so that the same problem is less likely to return unnoticed. Finally, explain the cause and the fix. This gives the next developer a useful starting point if a similar failure occurs.

### 中文对照

1. 程序失败时，立即修改代码往往不如先收集证据有用。首先，描述预期行为和实际结果。然后，找到一组精简、可重复的步骤来触发问题。能够复现的故障，比只被描述为“有时候会出问题”的故障更容易调查。
2. 仔细阅读错误信息。异常通常具有类型和消息，而堆栈跟踪可以展示导致故障的一连串函数调用。错误出现的位置，不一定就是最初犯错的位置。无效数据可能早得多就已经进入了系统。
3. 在能够作出有效响应的层级处理错误。用户界面可以显示有帮助的提示，而较低层则向调用方报告原因。捕获所有异常再忽略它们，可能会掩盖不正常的行为。清理工作仍然可能是必要的，因此即使操作失败，也应该释放已打开文件等资源。
4. 找到原因之后，进行有针对性的修改，并重复最初的复现步骤。在适当的时候增加回归测试，降低同一个问题再次出现却未被发现的可能性。最后，解释问题原因和修复方式。如果发生类似故障，这些记录能够为下一位开发者提供有用的调查起点。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| expected / actual | 预期的 / 实际的 | expected behavior；actual result |
| reproduce | 复现 | reproducible：可复现的 |
| exception | 异常 | catch / raise an exception |
| stack trace | 堆栈跟踪 | trace：追踪、跟踪记录 |
| underlying | 根本的、底层的 | underlying cause：根本原因 |
| caller | 调用方 | call：调用；被调用方为 callee |
| release resources | 释放资源 | release 在此不是“发布版本” |
| regression test | 回归测试 | 检查问题是否在后续修改中重现 |

### 文档句型拆解

- **A failure that can be reproduced is easier to investigate.** `that can be reproduced` 修饰 `failure`；主干是 `A failure is easier to investigate`。
- **The location where an error appears is not always the place where the underlying mistake was made.** 两个 `where` 从句分别修饰 `location` 和 `place`。先识别两个地点，再理解它们不一定相同。
- **Resources should be released even when an operation fails.** `even when` 表示“即使在……时也”。可迁移为：`The connection should be closed even when the request fails.`

### 复述与迁移

- 用英语解释：为什么错误出现的代码行不一定就是根本原因所在？
- 回想最近修复的一个问题，分别用一句英文写出预期结果、实际结果、原因和修复方式。

## 06. Working with Asynchronous Tasks

**主题：异步与执行顺序。背诵线索：等待外部结果 → Promise → 顺序依赖 → 结果过期。**

### 英文正文

Some operations spend much of their time waiting. A request may wait for a remote server, and a file operation may wait for storage. If a user interface cannot respond during that wait, the application feels frozen. Asynchronous programming allows the program to organize this work without requiring every operation to finish immediately.

In JavaScript, a promise represents the eventual outcome of an operation. It can be fulfilled with a value or rejected with a reason. Inside an async function, await pauses the continuation of that function until the promise settles. This does not, by itself, move expensive computation to another thread or make it faster.

The order of operations still matters. If one request needs an identifier returned by another, the second request must wait for the first result. Independent requests may be started together. However, starting several operations does not mean that every part of them runs in parallel. Concurrency and parallel execution describe different aspects of a system.

Always consider failure and changing user intent. A search request may finish after the user has already entered a new query. In that case, an older result should not replace the newer one. Clear loading states, appropriate error handling, and checks for outdated results help an asynchronous interface remain understandable and correct.

### 中文对照

1. 有些操作的大部分时间都在等待。网络请求可能在等待远程服务器，而文件操作可能在等待存储设备。如果用户界面在等待期间无法响应，应用就会让人感觉卡住了。异步编程让程序能够组织这些工作，而不要求每项操作都立即完成。
2. 在 JavaScript 中，Promise 表示某项操作最终的结果。它可以携带一个值兑现，也可以携带一个原因被拒绝。在异步函数内部，`await` 会暂停该函数后续部分的执行，直到 Promise 的状态确定。这本身不会把耗时计算移到另一个线程，也不会让计算变快。
3. 操作顺序仍然重要。如果一个请求需要另一个请求返回的标识符，那么第二个请求必须等待第一个结果。彼此独立的请求可以一起启动。不过，启动多个操作，并不意味着它们的每个部分都在并行运行。并发与并行执行描述的是系统的不同方面。
4. 始终考虑失败情况，以及用户意图的变化。搜索请求完成时，用户可能已经输入了新的查询。在这种情况下，旧结果不应该覆盖新结果。清晰的加载状态、恰当的错误处理，以及对过期结果的检查，有助于让异步界面保持易于理解且行为正确。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| asynchronous | 异步的 | synchronous：同步的；async：常用缩写 |
| promise | 表示异步结果的对象 | 在这里不是普通意义上的“承诺” |
| fulfill / reject | 兑现 / 拒绝 Promise | fulfilled / rejected |
| settle | 状态确定：已兑现或已拒绝 | 不等于“一定成功” |
| continuation | 后续执行部分 | continue：继续 |
| thread | 线程 | a worker thread：工作线程 |
| concurrency / parallelism | 并发 / 并行 | 能交错推进，不代表同时执行 |
| outdated result | 已过期、不再适用的结果 | outdated：过时的 |

### 文档句型拆解

- **A promise represents the eventual outcome of an operation.** `represents` 用于定义某个对象表示什么；`eventual` 表示最终的。可迁移为：`This value represents the current connection state.`
- **This does not, by itself, move expensive computation to another thread.** `by itself` 限定“仅凭这一点”；`does not` 否定整个动作。技术文档常这样避免过度推断。
- **A search request may finish after the user has already entered a new query.** `after` 说明时间先后；`has already entered` 强调新输入在返回结果之前就已经发生。

### 复述与迁移

- 用英语解释为什么给一个函数加上 `async` 不等于让其中的计算自动变快。
- 描述一个搜索框可能出现的旧结果覆盖新结果的问题，并用 `should not` 写出期望行为。

**延伸阅读：** [MDN：Introducing asynchronous JavaScript](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Async_JS/Introducing)。进一步阅读其后续 Promise 教程，区分异步、阻塞和并行。

## 07. Testing Observable Behavior

**主题：测试与断言。背诵线索：明确行为 → 安排执行断言 → 测试范围 → 有效失败。**

### 英文正文

A useful test describes behavior that matters to a user or another part of the system. Instead of checking every internal detail, it asks whether a clear requirement is satisfied. For a function that calculates a total price, the important result may be the amount returned for a given set of items.

Many tests follow a simple structure: arrange, act, and assert. First, prepare the input and any required state. Next, perform the operation being tested. Finally, compare the actual result with the expected result. A descriptive test name should explain the situation and the behavior, so that a failure gives the reader a useful clue.

Different tests cover different boundaries. A unit test examines a small piece of behavior, while an integration test checks whether components work together. A test double can replace an external dependency when a controlled response is needed. However, a simulated response does not prove that the real service still follows the same contract.

Include meaningful failure cases as well as successful ones. Missing input, empty results, and denied access may reveal problems that a normal example does not. Keep tests deterministic where possible, and investigate unexpected failures. Tests are most valuable when they detect important changes and explain them clearly, rather than merely increasing the number of checks.

### 中文对照

1. 有用的测试会描述对用户或系统其他部分有意义的行为。它不去检查每一个内部细节，而是判断一项明确的要求是否得到满足。对于计算总价的函数，重要的结果可能是：给定一组商品时，它返回了什么金额。
2. 许多测试遵循一种简单结构：安排、执行和断言。首先，准备输入及必要状态。接下来，执行被测试的操作。最后，把实际结果与预期结果进行比较。具有描述性的测试名称应该说明场景和行为，这样测试失败时，读者就能获得有用的线索。
3. 不同测试覆盖不同边界。单元测试考察一小块行为，集成测试则检查组件能否协同工作。需要可控的响应时，可以用测试替身替代外部依赖。不过，模拟出的响应并不能证明真实服务仍然遵循同样的契约。
4. 除了成功情况，也要包含有意义的失败情况。缺失输入、空结果和访问被拒绝等情况，可能暴露普通示例无法发现的问题。尽可能让测试结果具有确定性，并调查意料之外的失败。测试最有价值的地方，是发现重要的行为变化并清楚地解释它们，而不只是增加检查数量。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| observable behavior | 可观察到的行为 | observe：观察；observation：观察结果 |
| satisfy a requirement | 满足要求 | satisfied：得到满足的 |
| arrange / act / assert | 安排 / 执行 / 断言 | 常见测试组织方式 AAA |
| assertion | 断言 | assert：断言、检查条件 |
| unit test | 单元测试 | unit：单元 |
| integration test | 集成测试 | integrate：集成 |
| test double | 测试替身 | 可包含 stub、mock 等不同形式 |
| deterministic | 确定性的 | 在受控的相同条件下产生一致结果 |

### 文档句型拆解

- **It asks whether a clear requirement is satisfied.** `whether` 引出需要判断的命题；`is satisfied` 表示要求被满足。阅读断言说明时经常遇到这种结构。
- **Perform the operation being tested.** `being tested` 修饰 `operation`，相当于 `that is being tested`。可迁移为：`Inspect the data being processed.`
- **A simulated response does not prove that the real service still follows the same contract.** `prove that` 表示证明某个判断；`still` 强调行为是否持续成立。`contract` 在此是接口约定。

### 复述与迁移

- 用英语讲出 Arrange、Act、Assert 三个阶段分别做什么。
- 为你熟悉的函数设计一个正常情况和一个边界情况，并用英语描述预期结果。

**延伸阅读：** [pytest 官方文档：How to write and report assertions in tests](https://docs.pytest.org/en/stable/how-to/assert.html)。重点看断言失败时如何展示实际值，以及怎样检查预期异常。

## 08. Making Changes as a Team

**主题：分支、提交与合并。背诵线索：聚焦修改 → 描述提交 → 审查 → 解决冲突。**

### 英文正文

Software development is a shared activity, even when one person writes most of the code. Other people need to understand, review, and maintain the result. A useful change therefore includes more than working code. It also includes a clear explanation of the problem, the chosen solution, and the behavior that will change.

A branch allows a developer to work on a line of development without immediately changing the team's main branch. Keep the work focused on a specific purpose. Small, coherent commits are easier to inspect than a large collection of unrelated edits. A commit message should explain the change clearly enough to be useful later.

Before requesting a review, inspect your own diff and run the checks relevant to the change. Describe how the behavior was verified and mention any known limitations. During review, discuss the code and its consequences. A question about an assumption can be more useful than a comment that only expresses a personal preference.

When branches contain conflicting changes, Git may require you to resolve the conflict before completing a merge. Read both versions and decide what the combined result should mean. Removing conflict markers is only part of the work. The final code must still behave correctly, so verify the affected behavior after the conflict is resolved.

### 中文对照

1. 软件开发是一项协作活动，即使大部分代码由一个人编写也是如此。其他人需要理解、审查和维护结果。因此，一项有用的修改不只包含能运行的代码，还应清楚解释问题、所选择的解决方案，以及哪些行为将发生变化。
2. 分支允许开发者沿着一条开发路线工作，而不立即改变团队的主分支。让工作聚焦于一个具体目的。规模较小、内容连贯的提交，比大量不相关修改的集合更容易检查。提交说明应该把修改解释得足够清楚，以便将来仍然有参考价值。
3. 请求审查之前，先检查自己的差异内容，并运行与本次修改相关的检查。描述行为是如何得到验证的，并说明已知限制。在审查中，应讨论代码及其影响。针对某个假设提出问题，可能比仅表达个人偏好的评论更有帮助。
4. 当不同分支包含互相冲突的修改时，Git 可能要求先解决冲突，才能完成合并。阅读两个版本，判断合并后的结果应该表达什么。删除冲突标记只是工作的一部分。最终代码仍然必须行为正确，因此解决冲突后，要验证受影响的功能。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| maintain | 维护 | maintenance：维护；maintainer：维护者 |
| branch | 分支 | main branch：主分支 |
| commit | 提交；一次提交记录 | 与数据库事务提交语境不同 |
| coherent | 连贯的、围绕同一目的的 | coherent commits：内容连贯的提交 |
| diff | 差异内容 | inspect a diff：检查代码差异 |
| assumption | 假设、前提 | assume：假定 |
| conflict | 冲突 | resolve a conflict：解决冲突 |
| merge | 合并 | merge branches：合并分支 |

### 文档句型拆解

- **A branch allows a developer to work ... without immediately changing the team's main branch.** `allow somebody to do` 表示允许某人做某事；`without + 动名词` 表示不发生另一动作。
- **Describe how the behavior was verified and mention any known limitations.** `how...` 是 `describe` 的宾语；`known limitations` 是技术说明中的常见搭配。
- **Git may require you to resolve the conflict before completing a merge.** `require somebody to do` 表示要求某人执行操作；`before + 动名词` 说明操作顺序。

### 复述与迁移

- 用英语解释：为什么删掉冲突标记不代表冲突已经被正确解决？
- 为最近的一次修改写三句英文：原来有什么问题、现在如何工作、做了什么验证。

## 09. Checking Identity and Permission

**主题：认证与授权。背诵线索：确认身份 → 检查权限 → 最小权限 → 拒绝与验证。**

### 英文正文

A system needs to distinguish between knowing who a user is and deciding what that user may do. Authentication establishes an identity, while authorization determines whether an action is permitted. A user who has signed in successfully is not automatically allowed to read every record or change every setting in the application.

Imagine a service that stores private project notes. A request may contain a valid access token and the identifier of a note. The server still needs to check whether that identity has permission to access that particular note. Trusting the identifier simply because it came from the client would leave an important check missing.

Permissions should be limited to what the task requires. A service that only reads reports does not need permission to delete them. Access checks must be enforced on the server for protected operations. Hiding a button in the user interface can improve the experience, but it does not prevent someone from sending a request directly.

If the application cannot establish that access is allowed, it should deny the operation. Make this behavior explicit and test it. Include cases involving another user's data, missing credentials, and insufficient permissions. Clear rules are easier to review than scattered exceptions, and they help developers understand how to add new features without accidentally exposing protected information.

### 中文对照

1. 系统需要区分两件事：知道用户是谁，以及决定该用户可以做什么。认证用于确定身份，授权用于判断某个动作是否被允许。成功登录的用户，并不自动拥有读取应用中所有记录或修改所有设置的权限。
2. 想象一个保存私人项目笔记的服务。请求可能包含一个有效的访问令牌，以及某条笔记的标识符。服务器仍然需要检查该身份是否有权访问那一条特定笔记。仅因为标识符来自客户端就相信它，会漏掉一项重要检查。
3. 权限应该限制在任务所需的范围内。一个只读取报告的服务，并不需要删除报告的权限。对于受保护的操作，访问检查必须在服务端落实。在用户界面中隐藏按钮可以改善体验，但不能阻止别人直接发送请求。
4. 如果应用无法确认访问已获允许，就应该拒绝该操作。明确规定这种行为，并对其进行测试。测试情况应包括其他用户的数据、缺失的凭据，以及权限不足。清晰的规则比四处分散的例外更容易审查，也能帮助开发者理解如何新增功能，而不意外暴露受保护的信息。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| authentication | 认证：确认身份 | authenticate：进行认证 |
| authorization | 授权：判断访问权限 | authorize：授权 |
| identity | 身份 | establish an identity：确定身份 |
| permission | 权限、许可 | permitted：被允许的 |
| credentials | 身份凭据 | 与 permission 不同 |
| enforce | 强制执行、落实 | enforce access checks：落实访问检查 |
| deny | 拒绝 | deny access：拒绝访问 |
| insufficient | 不足的 | insufficient permissions：权限不足 |

### 文档句型拆解

- **Authentication establishes an identity, while authorization determines whether an action is permitted.** `while` 在此表示对比，不是“当……时”；`whether` 引出权限判断。
- **A user who has signed in successfully is not automatically allowed to read every record.** `who...` 修饰 `user`；关键限制是 `not automatically allowed`，不要因为看见登录成功就忽略后半句。
- **Hiding a button ... does not prevent someone from sending a request directly.** `prevent somebody from doing` 表示阻止某人做某事；`does not` 否定这种阻止能力。

### 复述与迁移

- 不使用中文，用两句话解释 authentication 和 authorization 的区别。
- 为“查看私人笔记”写一句允许条件，再用 `otherwise` 写出不满足条件时的行为。

**延伸阅读：** [OWASP：Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。重点阅读最小权限、默认拒绝和请求级权限验证。本篇是学习材料，不是完整的安全实现清单。

## 10. Improving Performance with Evidence

**主题：性能与缓存。背诵线索：定义问题 → 测量定位 → 缓存取舍 → 比较验证。**

### 英文正文

When an application feels slow, first define what slow means. A page may take too long to become usable, a search may respond late, or a background job may process too few records. These are different problems. Choosing a useful measurement helps the team discuss the same behavior instead of relying only on impressions.

Measure the application under conditions that resemble its intended use. Record the input size, the environment, and the steps used in the measurement. Then identify where time or resources are being spent. A slow response might come from a database query, a remote request, or repeated computation. The most visible code is not necessarily the main bottleneck.

Caching can help when the same result is needed repeatedly. Instead of calculating or fetching it every time, the application stores a result for later reuse. However, cached data can become outdated. The design must explain when the result expires or is invalidated, and whether different users are allowed to share the same cached value.

After making an improvement, repeat the measurement and check correctness as well as speed. A faster implementation is not useful if it returns the wrong result. Keep the change only when the evidence supports it, and document the tradeoff. Good optimization makes a particular workload better while keeping the system's required behavior intact.

### 中文对照

1. 当应用让人感觉很慢时，先定义“慢”具体指什么。可能是页面需要很久才能使用，搜索返回得太迟，也可能是后台任务处理的记录太少。这些是不同的问题。选择有用的衡量指标，可以帮助团队讨论同一种行为，而不是只凭印象判断。
2. 在接近预期使用方式的条件下测量应用。记录输入规模、环境，以及测量时使用的步骤。然后找出时间或资源花在了哪里。响应慢可能来自数据库查询、远程请求，或者重复计算。最显眼的代码不一定是主要瓶颈。
3. 当同一个结果被反复需要时，缓存可能有所帮助。应用把结果存下来供以后复用，而不是每次都重新计算或获取。不过，缓存的数据可能会过期、不再符合实际情况。设计必须说明结果何时到期或失效，以及不同用户是否可以共享同一个缓存值。
4. 做出改进之后，重新测量，并同时检查正确性与速度。如果返回的是错误结果，那么更快的实现也没有意义。只有证据支持时才保留修改，并记录其中的取舍。好的优化会改善某种具体工作负载下的表现，同时保持系统所要求的行为完整不变。

### 核心词汇与搭配

| 表达 | 本文含义 | 联想记忆 |
|---|---|---|
| measurement | 测量、测量结果 | measure：测量 |
| input size | 输入规模 | size 不一定是文件字节数 |
| bottleneck | 瓶颈 | identify a bottleneck：定位瓶颈 |
| computation | 计算 | compute：计算；recompute：重新计算 |
| cache / caching | 缓存 / 使用缓存 | cache hit：缓存命中 |
| expire / invalidate | 到期 / 使失效 | expiration / invalidation |
| tradeoff | 取舍、权衡 | 例如速度、内存和数据新鲜度之间的取舍 |
| workload | 工作负载 | workload-specific：针对特定负载的 |

### 文档句型拆解

- **Measure the application under conditions that resemble its intended use.** `under conditions` 表示在某种条件下；`that...` 修饰 `conditions`；`intended use` 表示预期用途。
- **Instead of calculating or fetching it every time, the application stores a result for later reuse.** `instead of + 动名词` 表示用后一种方式替代前一种方式；`for later reuse` 表示目的。
- **A faster implementation is not useful if it returns the wrong result.** `if` 给出否定评价成立的条件。可迁移为：`A cached response is not suitable if it contains another user's data.`

### 复述与迁移

- 用英语解释为什么优化之前和之后都需要测量。
- 为自己的项目选一个适合缓存的结果，说明何时生成、何时失效，以及是否允许用户间共享。

**延伸阅读：** [MDN：Performance fundamentals](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Fundamentals)。关注以用户体验为中心的性能目标和测量；本篇的缓存场景用于练习技术方案中的条件与取舍表达。
